PACIFIC.EXE · déroulement et conversations

Pacific Strike : déroulement et conversations

Ce que le code de PACIFIC.EXE fait des scripts de GAMEFLOW.IFF et de CONV.PAK, comparé à Strike Commander (OPTEST.EXE). Les deux formats ressemblent à ceux de Strike Commander, mais les arguments, les commandes et la compression ont changé.

Les commandes portent le nom de Strike Commander (GAMEFLOW_SYSTEM.md § 5.2, CONV_SYSTEM.md § 2) quand elles font la même chose ; un nom suivi de * est proposé ici. Les nombres sont en décimal. Référence texte : analysis/pacific/README.md.

  • 42 commandes de déroulement
  • 3 379 scripts EFCT lus sans reste
  • 283 conversations lues sans reste
  • 1942 – 1945 date de campagne
1

Programme et données

  • Un seul exécutable pour le vol et le hors-vol. Strike Commander en a deux (STRIKE.EXE, OPTEST.EXE). Même compilateur (Borland C++ 1991), mêmes overlays VROOMM.
  • Listing reconstruit (pas de base IDA) : source/pacific.asm, 588 segments dont 176 overlays, 6 069 fonctions. 1 138 noms repris des fonctions identiques de STRIKE.EXE et d'OPTEST.EXE.
  • PACIFIC.DAT est une archive TRE comme BIGTRE.TRE (600 fichiers).
  • Toutes les entrées des PAK sont compressées en PKWARE DCL (« implode ») : marque 3 dans la table du PAK, puis 4 octets de taille, puis le flux (octets 00 06). Cela vaut pour CONV.PAK comme pour CONVSHPS.PAK, CONVPALS.PAK, OPTSHPS.PAK… Les entrées vides ont la marque 7.

Variables et drapeaux

Les scripts désignent par un même numéro sur 2 octets soit une variable, soit un drapeau :

  • 0 à 255 : une variable de 2 octets (tableau word_7D00A) ;
  • 256 et plus : un bit, numéro − 256, dans un tableau de bits (word_7D00E).

Conditions REQU : 3 octets

Strike Commander : 2 octets (condition, drapeau). Pacific Strike : 1 octet de condition, puis le numéro sur 2 octets (bas, puis haut). Les 2 597 chunks se lisent sans reste ; on n'y trouve que REQUIRE_NOT_SET (2 393 fois) et REQUIRE_SET (4 447 fois).

Scripts EFCT

Gameflow_RunScript_604D4 fait comme Gameflow_RunScriptPairs_36CF d'OPTEST : même boucle, mêmes blocs ELSE / ENDIF / OR_GROUP, traités avant la table. La table a 42 cas (cmp bx, 29h).

Longueur d'une commande

Le code lit toujours 3 octets : la commande, l'octet a, l'octet b, et le mot a | b × 256. Il avance ensuite de 3 octets pour les commandes 0, 6, 7, 9, 10, 35 et 36, de 2 pour les autres, y compris quand la commande est sautée :

loc_60AF9:  inc  [bp+var_8]         ; +1 de plus pour 0, 6, 7, 9, 10, 35, 36
loc_60C72:  add  [bp+var_8], 2      ; +2 pour toutes
FormeCommandesOctets
commande, octettoutes les autres2
commande, mot (bas, haut)PLAY_CONV, SET_FLAG, CLEAR_FLAG, IF_NOT_FLAG, IF_FLAG3
commande, octet a, octet bSET_VARIABLE*, SET_DATE*3

Les 3 379 scripts des données se lisent avec cette règle sans reste. ENDIF porte presque toujours l'octet 4 (Strike Commander : 0) ; le code ne le lit pas.

Tests comptés pendant un saut (pour les ENDIF imbriqués) : 9, 10, 20, 21, 22, 28, 32.

Date et lieu

La campagne avance dans le temps. Les scripts écrivent le jour, puis la date :

SET_VARIABLE 81 16
SET_DATE 1 42
  • SET_VARIABLE* a b : variable a = b. Ici le jour du mois (variable 81).
  • SET_DATE* a b : mois a, année b (42 à 45, donc 1942 à 1945). Le code forme t = b × 12 + a, ajuste t avec des comptes de résultats (drapeaux 401 à 400 + mission courante : rang pair + 2 s'il n'est pas posé, rang impair − 1 s'il est posé ; variables 170 à 182 retirées, 185 à 194 ajoutées deux fois), garde au moins la date courante + 1 mois, puis année = t ÷ 12 (variable 83), mois = le reste (variable 82).
  • ADVANCE_MONTHS* n : t = année × 12 + mois + n, même découpage.

Écran de départ de TRAVEL

Avant la carte, l'écran de départ écrit deux lignes avec les chaînes de STRING.IFF (chunks de 20 octets par nom) :

  • le lieu : PLAC[variable 86] — « Pearl Harbor », « Marshall Islands », « Japanese waters », « the Coral Sea », « Midway Island », « the Central Pacific », « the Marianas », « the Philippines », « the Solomons » ;
  • puis la date : DATE[variable 82] (« January » à « December »), variable 81 (jour), variable 83 (année).

Les scripts posent la variable 86 juste avant TRAVEL* (§ 8). Le format exact de la ligne de date (chaîne de format dans le segment de code) n'est pas lu.

Différences avec Strike Commander

  • Pas d'identifiant de voix devant le texte.
  • 4 octets après chaque texte : la voix. Le code passe ces 4 octets à la lecture de la parole (fichier « strtspch ») si les 2 premiers ≠ 65 535 et que la parole est active. Dans les données : 65 535 dans 2 722 cas sur 2 731, 1 ou 2 dans les autres ; les 2 octets suivants n'ont pas de valeur suivie (restes de texte).

Le commandant à la carte (commande 17)

Dans une scène de groupe, GROUP_SHOT_COMMANDER* montre le commandant debout devant la carte, qui pointe un endroit avec sa baguette. La scène crée un calque (PointerLayer_Construct_62E1B) avec la figure, la liste d'images du script et le point visé (x, y).

Les données

  • Figure : yucmndr si le drapeau 2 128 est posé, sinon commndr. Ses images couvrent l'écran entier (en-tête 0 à 319 × 0 à 199) : l'image 0 est le commandant, les images 1 à 15 ne contiennent que le bras et la main (yucmndr a aussi les images 16 à 18, le commandant entier, poing levé).
  • Liste d'images : les n numéros du script, montrés dans l'ordre ; le calque avance d'une étape à chaque tour et reste sur la dernière (PointerLayer_Advance_62F57).
  • Point de la main : GAMEFLOW\PTR.IFF (FORM CPTR, chunk DATA), x et y (2 octets chacun) pour chaque image de la figure, en coordonnées d'écran. Lu à la création du calque (PointerLayer_LoadHandPoints_62F7E).
  • Cible : x, y de la commande, en coordonnées d'écran. Dans l'exemple (115, 70), c'est Kwajalein, l'endroit dont parle le texte.

Le dessin, à chaque étape

La méthode de dessin du calque (PointerLayer_Draw_62EF2) fait, dans cet ordre :

  1. la baguette : un trait de couleur 15 (PointerLayer_DrawStick_630DA) qui part du point de la main de l'image courante. À la dernière étape, il va jusqu'à la cible. Avant, il va jusqu'au point de la main décalé de l'écart entre le point de la main de la dernière image et la cible, en valeurs absolues (PointerLayer_StickOffset_6308B) : la baguette garde sa direction pendant que le bras se lève.
  2. l'image 0, toujours (sub_6A514 avec l'image 0) ;
  3. l'image courante de la liste (Layer_DrawAtOwnPos_66BEC).

À la dernière étape, le code retire de y le décalage vertical du groupe de calques ; sa valeur n'a pas été lue. Avec 0, la baguette tombe sur Kwajalein.

Répliques conditionnelles

IF_FLAG* n met une marque de saut si GameVar_Get_56414(n) = 0 ; ELSE* inverse la marque ; ENDIF* l'efface. Tant qu'elle est posée, GROUP_SHOT et CLOSEUP sont lus sans être affichés. Il n'y a pas d'imbrication. Conversation 68 :

CLOSEUP pan 22 ms_fpov3 160 128 "I mean, shucks, I wouldn't want to be shot down like that…" 244
IF_FLAG 76
ELSE
CLOSEUP pan 25 ms_fpov3 160 128 "But Noodles, he says we ought to kill every pilot, sir." 244
ENDIF
CLOSEUP air 25 ms_rpov 130 128 "I can't give you an answer, Wally. There's no regulation." 244

La réplique sur Noodles n'est dite que si le drapeau 76 n'est pas posé.

Scripts de mission : chargement et exécution par les objets

Lu le 2026-11-05, en comparant avec STRIKE.EXE (MISSION_SCRIPT_OPCODES.md). La mécanique est celle de Strike Commander ; les écarts sont listés au § 6.5.

6.1 Chargement (MissionScenario_LoadFromIFF_BD743)

Lit les chunks du fichier de mission (MISN : VERS, NAME, CAMP, TUNE, WRLD, FILE, CAST, AREA, SPOT, NUMS, MSGS, PROG, PART, TEAM, PLAY, LOAD, HOME). Appelée au départ en vol (par sub_877A0, pas encore nommée) et par l'écran MEDIT (Gameflow_MeditScreen_E3D9D).

  • PROG (ProgBuffer_LoadRawAndCountMarkers_BF8E9) : comme Strike Commander. Le bloc est copié tel quel ; le chargeur compte les octets nuls aux positions paires (cmp byte ptr es:[bx], 0 / add dx, 2) : ce sont les séparateurs entre les programmes. Un programme est désigné par son rang (ProgBuffer_FindSubProgramByIndex_51C42).
  • PART (PartEntry_AllocateArray_BF7F9) : nombre d'objets = taille du chunk ÷ 62 (mov bx, 3Eh / div bx, erreur si le reste n'est pas nul) ; 89 octets par objet en mémoire (imul ax, ax, 59h ; Strike Commander : 85). Chaque objet est lu par PartEntry_LoadAndResolveNames_BF3D5.

Le chunk PART n'a pas changé : 62 octets par objet, lus dans le même ordre aux mêmes places (mêmes variables de pile que PartEntry_LoadAndResolveNames_A9E3C de STRIKE.EXE). Seule la structure en mémoire change :

6.4 Encodage des instructions

Comme Strike Commander (Expr_VM_ReadNextToken_51D33, même lecture qu'Expr_VM_ReadNextToken_50F85) : un octet d'instruction, un octet d'argument ; tant que l'octet suivant vaut 9, il est sauté et l'octet d'après est un argument de plus (3 au plus). Exception : les 22 instructions de drapeau lisent un octet de plus (le numéro sur 2 octets), puis exigent l'octet 5 (§ 2.1).

6.5 Instructions : ce qui change

La table de l'interpréteur a toujours 209 cas (cmp bx, 0D0h). Toutes les instructions de Strike Commander sont traitées, et 12 de plus :

  • Instruction inconnue = erreur. Dans Strike Commander, le cas par défaut passe à l'instruction suivante. Dans Pacific Strike, il appelle la fonction d'erreur (push 911Bh / sub_1DDFE). Les instructions 5 et OP_SET_LABEL (8), qui ne font rien, ont donc maintenant leur propre cas.
  • Ordres (MissionScript_CallNativeHandler_53B0B) : au lieu d'un switch sur 161 à 191, une liste de 22 valeurs cherchée une à une (word_542E0). On y trouve tous les ordres de Strike Commander, plus 112, 173, 174, 175 et 193.

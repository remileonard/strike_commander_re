STRIKE.EXE · fichiers de données · référence de portage

Le modèle de données de Strike Commander

Ce document décrit ce que contiennent les fichiers du jeu et comment ils s'enchaînent : une mission désigne son monde, ses pilotes, ses zones et ses objets ; un objet désigne son modèle 3D et sa dynamique de vol ; un pilote désigne son profil de comportement. Chaque fiche donne la disposition sur disque, le sens de chaque champ et la façon dont le jeu s'en sert.

Toutes les dispositions viennent des lecteurs de STRIKE.EXE (segments annotés de analysis/annotated_segments/) ; le détail et les citations d'assembleur sont dans analysis/DATA_MODEL.md. Ce qui n'est pas prouvé est signalé comme tel.

Conventions de lecture

Repère
Y-up, comme libRealSpace : X et Z forment le plan horizontal (Z = profondeur), Y est l'altitude. Le jeu, lui, range ses vecteurs en Z-up (3ᵉ composante = altitude). Sur disque, un vecteur de 3 entiers se lit donc X = c0, Z = c1, Y = c2 : le 2ᵉ i32 est Z, le 3ᵉ est Y.
Unités
Distances en mètres, angles en degrés. Jamais de pieds.
Virgule fixe 24.8
Un i32 « 24.8 » se divise par 256 à la lecture (256 = 1,0). Un entier de 8 ou 16 bits que le code décale de 8 (shl 8) se lit tel quel (ex. un cap de 180 = 180°).
Ordre des octets
Tailles de chunk IFF en big-endian ; tous les champs internes en little-endian.
Index
Un index désigne le rang d'un enregistrement dans son chunk, à partir de 0. Un index hors liste (souvent 0xFFFF ou 0xFF) veut dire « aucun ».

Le conteneur IFF

Tous les fichiers de données (sauf la sauvegarde) sont des IFF. Un fichier est une arborescence de blocs :

FORM <type>   taille BE   ← conteneur : 4 octets de type puis des sous-blocs
  CHUNK <tag> taille BE   ← données ; paddé à une longueur paire
  FORM <type> …           ← conteneurs imbriqués, récursifs
  CAT  <type> …           ← concaténation d'éléments
PACK : table [offset u32 × N] → enregistrements de taille variable, parfois compressés LZW
  • Tailles big-endian, champs little-endian. Le jeu lit les champs avec des primitives u8 / u16 / u32 / N octets / chaîne C.
  • La recherche d'un chunk (seek_chunk) parcourt le niveau courant jusqu'à trouver le tag demandé : l'ordre des chunks n'importe pas pour ceux que le lecteur cherche par tag.
  • LZW : codes de 9 à 12 bits, 256 symboles + clear (256) + fin (257), premier code libre 258 — paramétrage de type GIF.
  • Archive PAK (terrain) : u32 taille_fichier, puis u32 (offset | 0xE0000000) × N, puis les données. Les PAK s'emboîtent.

OBJECTS\*.IFF

Objets 3D et catégories

  • racine FORM REAL
  • lecteur IFF_LoadModelMain

Un fichier d'objet contient FORM REAL → FORM OBJT → un sous-FORM qui fixe la classe de l'objet. Le jeu essaie les types dans l'ordre ci-dessous et garde le premier présent. Chaque classe renvoie une catégorie, que l'IA utilise pour choisir ses cibles (6 avion, 8 missile, 0x13 défense fixe).

JETP → DYNM

Dynamique de vol d'un avion

  • dans OBJECTS\<avion>.IFF
  • struct JDYN 197 o
  • codes d'erreur A001 → A005

Le FORM DYNM d'un avion regroupe 5 chunks lus en séquence. Les armes ont à la place un seul chunk de dynamique (MISS, GBMB, DURD, AGRV, SURF, PARA).

FORM JETP
 └─ FORM DYNM
     ├─ DYNM   u32            masse à vide (÷256)
     ├─ ATMO   u32 (+ bloc)   modèle d'atmosphère (partagé par tous les avions)
     ├─ THRS   u32 + 3× u8    poussée maximale avec PC (÷256) + 3 fractions moteur
     ├─ STBL   u32            stabilité / autorité de tangage
     └─ JDYN   73 octets      enveloppe de vol (28 champs)

Champs principaux

Champ (struct)Sens
THRS u8 ×3fraction de poussée sans PC (MIL) ; fraction à la vitesse de référence ; échelle de la vitesse où la poussée s'annule
+0x69capacité carburant (copiée en carburant courant +0x6D ; à 0 → extinction moteur)
+0x33coefficient de consommation
+0x37 / +0x3Btraînée ajoutée par l'aérofrein / par le train sorti
+0x3F / +0x43traînée au sol (roulage), et son supplément aérofrein sorti
+0x4Bangle d'incidence de décrochage (u8, degrés)
+0x4C / +0x4Dcalage de l'aile (toujours ajouté à l'incidence) / incrément des volets
+0x59vitesse de référence (F-16 : 50 m/s) : sous elle, le taux de roulis diminue ; effet de sol
+0x5Dcoefficient de traînée induite
+0x61gain de portance / agilité de la cellule
+0x71taux de roulis maximal (°/s)
+0x47accélération de roulis maximale (°/s²)
+0x80 / +0x82 / +0x84vitesses de consigne de l'IA : poursuite max (déf. 500), min (100), croisière (231)
+0x86seuil de distance de l'IA (déf. 11005)

Le modèle de vol complet (portance, traînée, poussée, asservissement) est décrit dans PHYSICS.md et DATA_MODEL.md §6.2.

INTEL\<nom>.IFF

Profil de pilote

  • racine FORM PROF
  • chargé pour chaque pilote IA
  • jamais pour le joueur

Le nom vient du chunk CAST de la mission : un pilote nommé STERN charge INTEL\STERN.IFF. Le fichier contient sa voix radio et son comportement.

FORM PROF
 ├─ VERS   u16 (= 2)
 ├─ FORM RADI                      la radio
 │   ├─ SPCH  u8 (optionnel)       jeu de voix INTEL\SPEECH\*.PAK
 │   ├─ INFO  u16 id + nom + indicatif (chaînes C)
 │   ├─ OPTS  lettres : ordres/questions qu'on peut lui adresser
 │   └─ MSGS  (u8 index, chaîne C)… : répliques (index partagés dans tout le jeu)
 └─ FORM _AI_                      le comportement
     ├─ AI\0_ marqueur vide
     ├─ MVRS  table de manœuvres pondérées (voir MVRS_MANOEUVRES.html)
     ├─ GOAL  jusqu'à 10 sélecteurs de comportement
     └─ ATRB  10 octets d'attributs, 0 à 16

La mission : FORM MISN

Une mission est construite comme une pièce de théâtre : CAST = la distribution (les pilotes), PLAY = la pièce, découpée en SCNE = scènes, PROG = les didascalies (scripts). Les chunks sont lus dans cet ordre par MissionScenario_LoadMainRecord_A8331 :

3TUNEpiste musicale (u8)
4WRLDsous-FORM obligatoire : FILE = nom du monde (8 car.), ou monde en ligne
5CASTnoms de pilotes
6AREAzones géographiques
7SPOTpoints rattachés à une zone
8NUMSvariables numériques du script
9MSGSmessages
10FLAGdrapeaux d'événement

CAST

Noms de pilotes

  • enregistrements 9 o
  • nombre = taille ÷ 9
  • lecteur PLAY_LoadCASTTeamNames_A9956
OctetTypeChamp
0x00char[8]nom (PLAYER, STERN, NULL, TEAM0…)
0x08u8zéro de fin

Chaque objet PART désigne son pilote par un index dans cette liste. Le nom décide qui le pilote :

  • PLAYER → le joueur, sans profil ;
  • NETWORK → un joueur en réseau ;
  • tout autre nom → une IA, profil chargé depuis INTEL\<nom>.IFF.

Les ailiers : TEAM0, TEAM1, TEAM2

À la lecture, tout nom TEAMn est remplacé sur place :

  1. 1
    mission lancée depuis la campagne et n < 3 → n-ième nom du chunk TEAM de OP2MISN.IFF : les ailiers choisis par le joueur ;
  2. 2
    n ≥ 3 → le nom reste TEAMn ;
  3. 3
    mission chargée hors campagne → tous les TEAMn deviennent BILLY.

Ex. TEAM0 remplacé par BILLY charge INTEL\BILLY.IFF.

AREA

Zones géographiques

  • enregistrements 49 / 53 / 65 o selon la forme
  • pas de compteur
  • lecteur ExprSlot_ConstructMain_A974A

Une zone est un volume nommé : sphère, cylindre vertical ou boîte. Le jeu s'en sert pour savoir dans quelle zone se trouve le joueur (et donc quelle scène activer), et comme origine des SPOT et des objets PART. La première lettre de l'enregistrement donne la forme, donc sa taille.

OctetTypeChamp
0x00u8forme : 'S', 'C' ou 'B'
0x01char[32]nom (ex. « Strike Base »)
0x21i32référence X ÷ 256
0x25i32référence Z ÷ 256
0x29i32référence Y (altitude) ÷ 256

Suite selon la forme (÷ 256 → m)

FormeChampsTaille
'S' sphère0x2D rayon49
'C' cylindre0x2D hauteur, 0x31 rayon53
'B' boîte0x2D +X, 0x31 −X, 0x35 +Z, 0x39 −Z, 0x3D hauteur65

Test « le point est-il dans la zone ? »

  • Sphère : distance 3D au centre ≤ rayon.
  • Cylindre : Y ≤ y ≤ Y + hauteur et distance dans le plan X/Z ≤ rayon.
  • Boîte : X − (−X) ≤ x ≤ X + (+X), Z − (−Z) ≤ z ≤ Z + (+Z), Y ≤ y ≤ Y + hauteur.
  • À chaque tick, le jeu teste la position du joueur contre les zones des scènes actives et prend la première qui la contient.
SPOT

Points rattachés à une zone

  • enregistrements 14 o
  • nombre = taille ÷ 14
  • lecteur Mission_LoadSpotList_AA6C9

Un spot est une destination pour les ordres de mission (aller à, défendre…). Ce n'est pas la zone qui référence un spot : c'est le spot qui pointe vers sa zone, et sa position est relative au point de référence de la zone.

OctetTypeChamp
0x00u16index de la zone AREA
0x02i32décalage X ÷ 256
0x06i32décalage Z ÷ 256
0x0Ai32décalage Y ÷ 256
 
position = décalage + référence(zone)   si la zone existe
position = décalage                     sinon (coordonnées absolues)
PART

Objets de la mission

  • enregistrements 62 o fixes
  • nombre = taille ÷ 62
  • lecteur PartEntry_LoadAndResolveNames_A9E3C
  • activation PartEntry_ResolveSpawnPositionAndActivate_51EDC

Chaque enregistrement décrit un objet : avion, véhicule, base, repère de piste. Il dit quel modèle charger, quel pilote, où et comment le faire apparaître, son camp et ses scripts. L'objet n'existe dans le monde qu'une fois activé (par sa scène ou par le script).

OctetTypeChamp
0x00u16index CAST : le pilote
0x02char[8]type d'objet = fichier OBJECTS\<type>.IFF (ex. F-16DES, MIG21)
0x0Achar[8]type de remplacement une fois détruit
0x12char[8]nom chargé dans un composant de l'entité — rôle non tranché
0x1Au16index de la zone AREA
0x1Cu8mode de placement : 0 = relatif à la zone, ≠ 0 = relatif au joueur
0x1D / 0x21 / 0x25i32 ×3décalage X, Z, Y ÷ 256
0x29i16cap en degrés (absolu, ou ajouté au cap du joueur)
0x2Bi16vitesse initiale (0 = à l'arrêt) — unité non prouvée, m/s probable
0x2Du8camp : 1 = allié, 0xFF = ennemi, autre = neutre
0x2Eu8allié à suivre par défaut (index PART)
0x2Fu8inutilisé
0x30 / 0x32 / 0x34i16 ×3poste en formation derrière l'allié : côté (X), avant (Z), haut (Y), mètres
0x36 … 0x3Cu16 ×4scripts PROG : à l'activation, à chaque tick, à la destruction, à l'initialisation

À l'activation

  1. 1
    Modèle : le type normal, ou le type de remplacement si l'objet a déjà été détruit (ses scripts sont alors effacés). Nom vide → rien n'apparaît.
  2. 2
    Position : mode 0 → référence de la zone + décalage (comme un SPOT), cap absolu. Mode ≠ 0 → décalage exprimé dans le repère de l'avion du joueur (X côté, Z vers le nez, Y vers le haut de l'avion), cap = cap du joueur + cap du fichier.
  3. 3
    L'objet apparaît à plat (seulement tourné autour de la verticale), avec sa vitesse initiale le long du nez.
  4. 4
    Un avion à vitesse nulle est posé au sol, train sorti.
  5. 5
    Camp copié, ordre « suivre » donné vers l'allié, compteur d'objets actifs du camp incrémenté.

Drapeaux d'exécution (pas sur disque, champ +0x39 de l'entrée) : bit 0 actif ; bit 1 détruit ; bit 4 visible sur la carte de navigation ; bit 5 accompagne le joueur au pilote automatique.

PLAY / SCNE

Scènes

  • FORM PLAY → N chunks SCNE (≤ 32)
  • en-tête 24 o + liste d'objets
  • lecteur MissionPlay_LoadScenes_AA595

Une scène est un morceau de la mission rattaché à une zone : quand le joueur entre dans la zone, la scène s'active, fait apparaître ses objets et lance son script.

OctetTypeChamp
0x00u8active au départ
0x01u16index de la zone AREA (−1 = scène globale)
0x03 / 0x05 / 0x07i16 ×3scripts PROG : à l'activation, en quittant, à chaque tick (−1 = aucun)
0x09u8a sa propre position (1) ou utilise la zone (0)
0x0Au16candidat : cap en degrés (180 / 0 observés) — non tracé
0x0C / 0x10 / 0x14i32 ×3position X, Z, Y ÷ 256
0x18 …u16 × nliste d'objets : index dans PART, n = (taille − 24) ÷ 2

Points ouverts

  • PART : rôle du troisième nom (octet 0x12) et unité exacte de la vitesse initiale.
  • SCNE : le champ 0x0A (cap ?) n'est pas tracé dans le code.
  • Terrain : rôle de .OBJ et de l'octet libre des sommets .TRI ; placement des bâtiments d'aérodrome.
  • Objets : classes RNWY, EXPL, DEBR non lues.
  • ATRB : nom du 10ᵉ attribut.
  • Aucun fichier de mission réel n'est dans le dépôt : les formats AREA, SPOT, PART et CAST viennent du code seul.

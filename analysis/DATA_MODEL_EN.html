STRIKE.EXE · data files · porting reference

The Strike Commander data model

This document describes what the game files contain and how they link together: a mission names its world, its pilots, its areas and its objects; an object names its 3D model and its flight dynamics; a pilot names its behaviour profile. Each card lists the fields in the order in which they are stored in the file, with their type, size and meaning.

All layouts come from the readers in STRIKE.EXE; details and proofs are in analysis/DATA_MODEL.md and analysis/PHYSICS.md (in French). Anything not proven is flagged as such.

Reading conventions

Field order
Tables list the fields in file order, with no gaps unless stated. Just read them one after another.
Types
Integers are named by size and sign: uint8 1 byte (0 to 255) · int8 1 signed byte (−128 to 127) · uint16 2 bytes · int16 2 signed bytes · uint32 4 bytes · int32 4 signed bytes · float 4 bytes (see below) · unsigned char 1 character (a letter) · string[N] N characters padded with zeros.
float
A decimal number on 4 bytes. It is not stored as an IEEE float: it is a fixed-point number, read as a signed 4-byte integer and then divided by 256. In a hex editor you therefore see 256 times the value (12,800 for 50.0). Integers are read, unless stated, as is (a heading of 180 = 180°).
Frame of reference
Y-up, like libRealSpace: X and Z form the horizontal plane (Z = depth), Y is altitude. In the files, a 3-number vector is stored X, then Z, then Y: the 2nd is depth, the 3rd is altitude.
Units
Distances in metres, angles in degrees. Never feet.
Byte order
IFF chunk sizes are big-endian; all fields are little-endian (x86 order).
Field names
Field names are those of this document, not the game's (the binary contains none). A name followed by “assumed” or a description “role not established” flags a field whose meaning is not proven.
Index
An index is the rank of a record in its chunk, starting at 0. An index outside the list (often 65535, i.e. −1, or 255) means “none”.

The IFF container

All data files (except the saved game) are IFF: a tree of blocks.

BlockContents
FORMcontainer: 4-character tag, size (big-endian), 4-character type, then sub-blocks
CHUNKdata: 4-character tag, size (big-endian), then the data; padded to an even length
CATconcatenation of elements
PACKaddress table, then variable-size records, sometimes LZW-compressed
  • The game looks up a chunk by its tag in the current level: chunk order does not matter for the chunks it looks up this way.
  • LZW: 9- to 12-bit codes, 256 symbols, code 256 = reset, code 257 = end, first free code 258 (as in GIF). Observed on ALASKA.PAK: bits are read from least to most significant (GIF order), and the width grows to n + 1 bits when the table reaches 2ⁿ entries.
  • PAK archive (terrain): uint32 file size, then one uint32 address per sub-resource, then the data. PAKs nest. Observed on ALASKA.PAK:
    • the number of entries is not stored: the table ends at the first address, where the data starts;
    • the 3 high bits of an address are not part of the address: 111 = entry stored as is, 001 = compressed entry, which starts with its uncompressed size (uint32) followed by the LZW stream;
    • an empty entry has the same address as the next one (length 0).

SMKG: the smoke generator's INFO chunk

FieldTypeBytesDescription
smoke typeuint81number of the smoke model in the world's smoke set (SMOK chunk of WRLD)
durationfloat4seconds of emission
rise speedfloat4vertical speed of the particles (along Y)
intervalfloat4seconds between two particles
activation chanceuint162chance that the generator is active when created (out of ~100)
self-removaluint811 = the object disappears at the end of the duration; 0 = it only stops

This chunk is mandatory. The generator then reads the common chunks and ALGN.

EJEC: the DATA chunk

FieldTypeBytesDescription
value 1int324stored in memory by the loader; role not established
delayfloat4seconds before release
release heightint324metres: the object is released once below this height
released objectstringnname of the created object (the parachute), zero-terminated

When the delay has elapsed and the object is below the release height, the game creates the named object once only, at the same position, with the same orientation and the same speed. EJEC also has its own flight dynamics and can have a smoke trail (SMOK chunk).

SMOK: a mobile object's smoke trail

Oriented mobile objects (OMOB, EJEC…) can have an optional SMOK chunk: they then leave a smoke trail, for example an aircraft falling in flames.

FieldTypeBytesDescription
smoke typeuint81number of the smoke model in the world's smoke set
emission point Xfloat4metres, in the object's frame (side)
emission point Zfloat4metres, in the object's frame (nose axis)
emission point Yfloat4metres, in the object's frame (up)

F-16: X = 0, Z = −14, Y = 0: the smoke comes out 14 m behind the aircraft's centre.

  1. 1
    Ignition: the trail starts when the object is destroyed (and in some cases of ground contact), only if its model has a SMOK chunk.
  2. 2
    Every frame: the game computes where the emission point is now and where it was in the previous frame, then spreads particles along that segment. The trail therefore stays continuous even at high speed; the number of particles depends on the segment length and on the spacing given by the smoke model.
  3. 3
    Smoke set: smoke models come from the smoke set named by the world's SMOK chunk (SMOKESET). With no set loaded, no smoke is emitted (neither trail nor SMKG).

A component

FieldTypeBytesDescription

namestringnzero-terminated (at most 9 characters): FUEL, RUDDER, ELEVATOR, AILERON, LWING, RWING, ENGINE, LANDGEAR, FLAPS…

The game finds a component by its name. How a hit damages the components

  1. 1
    Damage points: given by what hits the aircraft. Any object: DAMG × min(v² ÷ 200, 10), where v is the sum of the two objects' speeds (m/s). A missile: that impact + 60 to 100 % of the max damage of its EXPL. A gun burst: WDAT damage × the multiplier from its INFO, from 100 % down to 50 % over its life. An explosion: the linear EXPL formula. Against the player, points are halved (at least 1).
  2. 2
    Zone hit: the name of the EXTE volume struck (FUSELAGE, LWING, RWING). If it is the global BIGSPHER sphere, the zone is drawn at random: fuselage 50 %, left wing 25 %, right wing 25 %.
  3. 3
    Distribution: the components of that zone are taken (17 at most), starting from a random one. Each absorbs what it has left (strength − damage) until the points run out.
  4. 4
    Loss of the aircraft: damage rate = sum of damage × 100 ÷ sum of strengths (100 if PLAYER is destroyed). Beyond the JINF threshold (30 % by default), the aircraft is lost.

When is the aircraft “on the ground”?

Every frame, the aircraft is landed if all these conditions are true, otherwise it is flying:

  1. 1
    it descends more slowly than field 12 (m/s);
  2. 2
    its roll is below field 14, and its attitude is between −field 16 and +field 15 (degrees);
  3. 3
    its horizontal speed is below field 13 (m/s);
  4. 4
    its gear is down and the pilot has not ejected.

If it touches down descending faster than half of field 12, it bounces: vertical speed = −(vertical speed + field 12 ÷ 4). Otherwise its negative vertical speed is cancelled.

The full flight model (lift, drag, thrust, control loop) is described in PHYSICS.md.
